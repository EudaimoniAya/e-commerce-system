# ADR-005：中间件栈与异常处理架构决策

- **状态**：已采纳
- **日期**：2026-07-26
- **背景**：为 e-commerce-system 新增统一 error JSON 契约（`{error: {code, message, request_id}}`）及 request_id 透传/生成。需要决定中间件注册方式、异常兜底方案、request_id 的 ContextVar 管理方式。

## 涉及文件

- `app/infra/logging/middleware.py` — RequestIDMiddleware
- `app/infra/errors/handlers.py` — 三个 handler（validation/http/unhandled）
- `app/infra/errors/register.py` — ExceptionMiddleware + UnhandledExceptionMiddleware 注册
- `app/main.py` — create_app 组装

## 决策 1：引入纯 ASGI 中间件解决 BaseHTTPMiddleware 的 ContextVar 丢失问题

### 问题

`@app.middleware("http")` 底层是 Starlette 的 `BaseHTTPMiddleware`，它内部使用 `anyio.create_task_group()` 以子任务方式运行下一层调用链。当子任务抛出异常时，task group 的取消/异常传播机制可能导致 ContextVar 回退到任务创建时的快照——即外层中间件设置的 ContextVar 值在异常处理块中读不到。

### 决策

对 **需要在异常路径下可靠读写 ContextVar** 的中间件（RequestIDMiddleware、UnhandledExceptionMiddleware），采用实现 `__call__(self, scope, receive, send)` 的纯 ASGI 类，通过 `app.add_middleware()` 注册。调用下一层时直接 `await self.app(scope, receive, send)`，无子任务，ContextVar 在整个请求生命周期保持一致。

不涉及 ContextVar 或异常路径的中间件（如计量、CORS 等），仍可使用 `@app.middleware("http")` 的便捷接口——不搞一刀切。

### 理由

| 方案 | 内部实现 | ContextVar 异常路径行为 |
|------|---------|----------------------|
| `@app.middleware("http")` | anyio task group 子任务 | 可能丢失 |
| 纯 ASGI class | 直接 await（同一调用链） | 始终稳定 |

RequestIDMiddleware 和 UnhandledExceptionMiddleware 都需要在异常路径下读取/写入 request_id，因此必须保证 ContextVar 稳定。对于不踩这个坑的场景，BaseHTTPMiddleware 的接口便利性仍是优势。

### 代价

- 纯 ASGI 中间件需要手动处理 scope/receive/send，不能享受 Request/Response 高级 API
- 修改响应头需要自定义 `send` 函数

### 备选方案

- 保留 BaseHTTPMiddleware，但放宽测试断言（不检查 request_id 非空）——已排除，因为 request_id 是日志审计的核心字段，必须可靠

## 决策 2：未捕获 Exception 用中间件兜底，不用 add_exception_handler(Exception)

### 问题

`app.add_exception_handler(Exception, handler)` 将 handler 注册到 `self.exception_handlers[Exception]`。`build_middleware_stack` 的分类逻辑把 `Exception` 分给 `ServerErrorMiddleware` 作为 `error_handler`。

ServerErrorMiddleware 的 `__call__` 在调用 handler 发送响应后，始终 `raise exc`。在生产环境（uvicorn）中这只是记日志，但在测试环境（httpx.ASGITransport，默认 raise_app_exceptions=True）中，异常的 re-raise 被 httpx 捕获并抛给测试代码，导致测试拿不到响应对象。

### 决策

- `RequestValidationError` 和 `HTTPException` → 通过 `app.add_exception_handler()` 注册到 ExceptionMiddleware（正常处理，不 re-raise）
- `Exception`（未捕获异常）→ 通过纯 ASGI `UnhandledExceptionMiddleware` 中间件兜底，在 ExceptionMiddleware 之上截获并返回 Response，不让异常到达 ServerErrorMiddleware

### 中间件栈顺序（从外到内）

```text
ServerErrorMiddleware          ← Starlette 内置，最外层兜底
RequestIDMiddleware            ← 纯 ASGI，设 ContextVar + loguru 绑定
UnhandledExceptionMiddleware   ← 纯 ASGI，截获未捕获 Exception，返回 Response
ExceptionMiddleware            ← Starlette 内置，处理 HTTPException/ValidationError
AsyncExitStackMiddleware       ← FastAPI 内置
Router                         ← 业务路由
```

### 理由

| 异常类型 | 处理方式 | 原因 |
|---------|---------|------|
| HTTPException（404/403/409 等） | ExceptionMiddleware | 预期中的业务异常，正常返回错误响应 |
| RequestValidationError（422） | ExceptionMiddleware | FastAPI 自动抛出，统一格式化为 error JSON |
| RuntimeError / ValueError / 其他未捕获 | UnhandledExceptionMiddleware 中间件 | 绕过 ServerErrorMiddleware 的 re-raise，保证测试能拿到响应 |

### 代价

- 多一层中间件（对比直接使用 add_exception_handler）
- 需要理解 build_middleware_stack 的分类逻辑才能解释为什么不能直接用 add_exception_handler

## 决策 3：request_id 用 ContextVar 存储，不依赖 request.state

### 问题

request_id 需要在请求全生命周期可访问，包括在异常路径（500 handler）中。

### 决策

使用 `contextvars.ContextVar` 存储 request_id，提供 `get_request_id()` 公共 API。

### 理由

| 方案 | 异常路径可访问性 | 线程安全 | 生命周期 |
|------|-----------------|---------|---------|
| `request.state.request_id` | 需要 Request 对象引用 | asyncio 安全 | 随 request 销毁 |
| `ContextVar` | 任意位置可读 | asyncio 安全 | 需手动 reset |
| 全局变量 | 可访问但竞争 | 线程不安全 | 全局 |

UnhandledExceptionMiddleware 的 handler 函数签名是 `(request, exc)`——它虽然有 Request 对象，但 handler 需要独立于 FastAPI 框架的逻辑层里也能读取 request_id（如日志记录），ContextVar 更适合。

### 代价

- 必须保证 request_id_middleware 在 UnhandledExceptionMiddleware 之外（先注册）
- 必须用纯 ASGI 形式（否则异常路径 ContextVar 丢失）
