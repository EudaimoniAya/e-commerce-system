# ADR-003：测试架构——四层分层与数据流约束

- **状态**：已采纳
- **日期**：2026-07-20
- **背景**：`test-architecture` change（2026-07-19）将测试代码重构为四层——Test Case / Test Fixture / Test Support / Test Utilities，并引入了 `PipelineResult`、`*Context`、`*ActionResult` 等数据容器。当前 `ordering-buyer-orders` change 的红阶段测试是该架构的第一次实际应用，暴露出理论主张与技术约束之间的张力，需要记录决策边界与遗留问题。

## 架构概览

```
┌─────────────────────────────────────────────────────┐
│  Test Case        test_*.py                          │
│  断言为主，不写 HTTP 逻辑，不互 import                 │
│  模块级常量可保留在文件内                              │
├─────────────────────────────────────────────────────┤
│  Test Fixture     conftest.py                        │
│  调 helper → fail-fast → 返回 *Context               │
│  不含业务逻辑（不直接 client.post）                     │
│  Context 不下沉到 helper                             │
├─────────────────────────────────────────────────────┤
│  Test Support     tests/support/helpers.py           │
│  helper 执行业务逻辑（HTTP 编排），返回 *ActionResult   │
│  helper 如实返回 status_code，不替 Case 断言           │
│  *Result 仅含本次调用的数据，不嵌套历史信息              │
│  PipelineResult 管理多步链：steps: tuple[object, ...] │
├─────────────────────────────────────────────────────┤
│  Test Utilities   tests/support/builders/ 等         │
│  构造合法 domain schema、类型投影                     │
└─────────────────────────────────────────────────────┘
```

## 数据流方向

```
helper  →  PipelineResult / *ActionResult    ← 只向上返回
fixture →  *Context(root: PipelineResult)    ← fixture 包装
Case    →  断言 root.step(XxxResult).body    ← 按需取用

禁止方向：Context 不流入 helper 签名
禁止方向：fixture 直接 client.post（业务逻辑应通过 helper）
禁止方向：Case 互 import
```

## 关键决策记录

### 1. ActionResult 不做树结构

`*Result` 只包含一次 HTTP 调用的数据（`status_code`、`body`、`request`），不记录子 `ActionResult` 引用。

- **理由**：避免胖对象。一个 `ConfirmedOrderResult` 如果嵌套记录 `CategoryResult`、`ProductResult`、`OrderResult`、`PayResult`，数据结构会随业务深度指数膨胀，且每个 Result 的 typing 不再是声明式的。
- **代价**：`PipelineResult` 以扁平 `tuple` 管理步骤链，历史信息不自动包含。

### 2. PipelineResult 作为多步链容器

`PipelineResult.steps` 是 `tuple[object, ...]`，通过 `step(T)` / `all(T)` 按类型取用。

- **理由**：扁平结构避免嵌套，取数路径可预测（`root.step(XxxResult)`），配合类型注解在重构时提供编译器保护。
- **代价**：两步产生同类 `XxxResult` 时无法通过 `step()` 区分，需通过下标或 `all()` 手工过滤。

### 3. Context 仅含 ActionResult，不含 Context

`*Context` 的字段类型约束为 `PipelineResult` 或 `*ActionResult`，不出现嵌套 `*Context`。

- **理由**：反模式 4（Context 嵌套 + 存储拷贝）已被记录为需要避免的问题；扁平 Context + 投影函数（`bearer_headers`）替代存储型便利字段。
- **代价**：取嵌套数据需要链式 `root.step(A).step(B)` 或跨 `root` 取不同类型，而非一次属性访问。

### 4. Fixture 从零组装

高层 fixture 必须显式声明所有前置依赖，向 helper 传入完整的 `PipelineResult` 等参数。

- **理由**：见下方「局部最优」分析。
- **代价**：底层 helper（如 `arrange_purchasable_product`）被频繁调用（ordering 域 26 次），且每个调用方都需自行准备 `shop_owner.root` 和 `admin.root`。

## 实际对照：旧代码反模式的解决

以下对照取自第三次重构前的 catalog 域代码（详见 `docs/troubleshooting/测试架构-旧模式反模式记录.md`），每一条反模式在当前架构中都有对应的约束拦截。

### 反模式 1：Test 文件当 Support 层 + Test 互 import

旧 catalog 测试中，`test_create_product.py` 内部定义了 `_create_product` helper，其他文件如 `test_public_products.py` 通过 `from tests.catalog.test_create_product import _create_product` 引用它：

```python
# ❌ 旧模式（catalog domain）
# tests/catalog/test_create_product.py
async def _create_product(
    client,
    admin_auth_headers: AdminAuthContext,
    shop_owner: ShopOwnerContext,
    *,
    is_published: bool = False,
    category_id: str | None = None,
) -> ProductResponse:                          # 返 domain schema，不是 Result
    ...
    response = await client.post("/products", ...)
    assert response.status_code == 201          # 替 Case 断言
    return ProductResponse.model_validate(...)

# tests/catalog/test_public_products.py
from tests.catalog.test_create_product import _create_product  # ❌ test 依赖 test
```

**当前约束**：
- Helper 全部迁入 `tests/support/helpers.py`，返回 `*Result` 而非 domain schema
- 禁止 `from tests.*.test_* import`（CI grep 拦截）
- Case 文件只保留断言和模块级常量

```python
# ✅ 当前模式（ordering domain）
# tests/support/helpers.py
async def create_product(
    client: AsyncClient, ...
) -> ProductResult:
    response = await client.post("/products", ...)
    return ProductResult(                     # 如实返回，不 assert
        status_code=response.status_code,
        body=_parse_product_body(response),
        ...
    )

# tests/ordering/test_create_order.py
from tests.support.helpers import arrange_purchasable_product  # ✅ 来自 support
```

### 反模式 2：Helper 内 assert 成功状态码

旧 `_create_product` 在内部 `assert response.status_code == 201`，导致负向测试（如"商品名重复 → 422"）无法复用同一个 helper。

**当前约束**：Helper 只返回 `*Result`，状态码断言在 Case 或 fixture fail-fast 中完成。

```python
# ✅ arrange_purchasable_product 如实返回失败状态
# tests/support/helpers.py
async def arrange_purchasable_product(...) -> PipelineResult:
    category = await create_category(...)
    if category.status_code != 201 or category.body is None:
        return PipelineResult(steps=(category,))  # 提前返回，不 assert
    product = await create_product(...)
    return PipelineResult(steps=(category, product))

# 断言在 Case 层
# tests/ordering/test_create_order.py
arranged = await arrange_purchasable_product(...)
product = arranged.step(ProductResult)
assert product.status_code == 201                 # ✅ Case 自己 assert
```

### 反模式 3：组合 helper 返回 Context（数据流倒置）

旧 `register_and_open_shop` 直接返回 `ShopOwnerContext`，把 fixture 的装配职责混进了 support 层。fixture 拿到后不做 fail-fast 就透传给 Case。

```python
# ❌ 旧模式
# conftest.py 内的 orchestrator
async def register_and_open_shop(...) -> ShopOwnerContext:
    registered = await register_user(...)
    auth = AuthContext(...)
    shop_result = await create_shop(...)
    return ShopOwnerContext(                    # helper 构造 Context
        status_code=shop_result.status_code,
        auth=auth, shop=shop_result.body, ...
    )

@pytest.fixture
async def shop_owner(client) -> ShopOwnerContext:
    return await register_and_open_shop(client)  # ❌ 无 fail-fast
```

**当前约束**：Helper 返回 `PipelineResult`，fixture 负责包 `*Context` 并 fail-fast。

```python
# ✅ 当前模式
# tests/support/helpers.py
async def register_and_open_shop(client) -> PipelineResult:
    registered = await register_user(client, ...)
    shop = await create_shop(client, ...)
    return PipelineResult(steps=(registered, shop))  # 返扁平链

# tests/conftest.py
@pytest.fixture
async def shop_owner(client) -> ShopOwnerContext:
    root = await register_and_open_shop(client)
    shop = root.step(ShopResult)
    if shop.status_code != 201 or shop.body is None:
        pytest.fail(f"开店 Setup 失败（status={shop.status_code}）")
    return ShopOwnerContext(root=root)          # ✅ fixture 包 Context
```

### 反模式 4：Context 嵌套 + 存储型便利字段

旧 `ShopOwnerContext` 内嵌 `auth: AuthContext`，同时重复存储 `headers`、`shop` 等字段，形成多份拷贝：

```python
# ❌ 旧模式
@dataclass
class ShopOwnerContext:
    auth: AuthContext                           # Context 嵌套
    shop: ShopResponse | None                   # 与 body 重复
    headers: dict[str, str]                     # 与 auth.headers 重复
    status_code: int                            # 两步 status 命名易混
```

**当前约束**：`*Context` 仅含 `root: PipelineResult`，数据通过 `step(T)` + 投影函数取用。

```python
# ✅ 当前模式
@dataclass(frozen=True)
class ShopOwnerContext:
    root: PipelineResult                        # steps=(RegisterResult, ShopResult)

# 用例内取数
shop_owner.root.step(ShopResult).body.id        # ✅ 不冗余
bearer_headers(shop_owner.root.step(RegisterResult))  # ✅ 投影函数
```

### 反模式 5：Setup fixture 不 fail-fast

旧 `shop_owner` fixture 透传失败状态，Case 被迫写防御性断言。

**当前约束**：所有 happy-path fixture 在返回前 `pytest.fail`。

```python
# ✅ 当前模式（所有 fixture 统一风格）
# tests/conftest.py
@pytest.fixture
async def authenticated_user(client) -> AuthContext:
    root = await register_authenticated(client)
    registered = root.step(RegisterResult)
    if registered.status_code != 201 or registered.body is None:
        pytest.fail(f"注册 Setup 失败（status={registered.status_code}）")
    return AuthContext(root=root)
```

## 从零组装的重复：ordering 域的真实数据

当前 5 个 ordering 测试文件中，`arrange_purchasable_product` 被调用了 **21 次**，`arrange_confirmed_order` 被调用了 **6 次**。每一次调用都从零传参：

```python
# 每个测试用例都要写这三行（或类似变体）
arranged = await arrange_purchasable_product(
    client,
    shop_owner=shop_owner.root,
    admin=admin_auth_headers.root,
    stock=10,
)
product = arranged.step(ProductResult)
assert product.status_code == 201
```

分布在 `test_create_order.py`（5 次）、`test_pay_order.py`（5 次）、`test_list_orders.py`（5 次）、`test_cancel_order.py`（3 次）、`test_shipments_and_receipt.py`（3 次）。

此外，每个测试用例的顶部都有相同的 Setup 断言模式：

```python
buyer = authenticated_user.root.step(RegisterResult)
assert buyer.status_code == 201
assert buyer.body is not None
```

这段代码在 11 个测试用例中重复出现，唯一差异是 buyer 变量名（`buyer` / `other_user`）。

### 跨店场景：从零组装走到极限

当测试需要**第二个店铺**的商品时（如跨店合单 422），从零组装的成本翻倍：

```python
# tests/ordering/test_create_order.py: test_cross_shop_multi_order_returns_422
arranged_a = await arrange_purchasable_product(
    client, shop_owner=shop_owner.root, admin=admin_auth_headers.root, stock=10,
)
product_a = arranged_a.step(ProductResult)
assert product_a.status_code == 201

other_shop = await register_and_open_shop(client)          # 第二个店铺：从零组装
assert other_shop.step(ShopResult).status_code == 201
arranged_b = await arrange_purchasable_product(            # 第二个商品：从零组装
    client, shop_owner=other_shop, admin=admin_auth_headers.root, stock=10,
)
product_b = arranged_b.step(ProductResult)
assert product_b.status_code == 201
```

此场景中 fixture 层提供的 `shop_owner` 不够用（它是单店铺上下文），第二个店铺必须在 Case 里从零注册。fixture 如果支持多店铺上下文，就能避免这段重复——但当前架构下 fixture 无法提供这种灵活性。

## Fixture 依赖的理想形式 vs 实际形式

以 `arrange_confirmed_order` 为例，对比 fixture 依赖的理想方案和当前的实际方案。

### 实际方案（当前）

Fixture 和 Case 各自显式传参：

```python
# tests/conftest.py — 当前没有 confirmed_order fixture，因为它依赖 purchasable_product
# 如果有，会是这样：

@pytest.fixture
async def confirmed_order(client, shop_owner, admin_auth_headers, authenticated_user):
    buyer = authenticated_user.root.step(RegisterResult)
    product_root = await arrange_purchasable_product(
        client, shop_owner=shop_owner.root, admin=admin_auth_headers.root, stock=10,
    )
    product = product_root.step(ProductResult)
    if product.status_code != 201:
        pytest.fail(...)
    created = await create_order(client, headers=bearer_headers(buyer), ...)
    paid = await pay_order(client, headers=bearer_headers(buyer), ...)
    return ConfirmedOrderContext(root=PipelineResult(steps=(product_root.steps, paid)))
```

注意这里：`arrange_purchasable_product` 的 `shop_owner.root` 和 `admin_auth_headers.root` 由调用方（fixture 本身或 Case）负责传递，而这两个参数恰好来自其他 fixture 的 `root` 字段。

### 理想方案（未采用）：Fixture 嵌套

```python
# 🚫 未采用的方案
@pytest.fixture
async def purchasable_product(client, shop_owner, admin_auth_headers) -> PurchasableProductContext:
    root = await arrange_purchasable_product(
        client, shop_owner=shop_owner.root, admin=admin_auth_headers.root,
    )
    return PurchasableProductContext(root=root, shop_owner=shop_owner, admin=admin_auth_headers)

@pytest.fixture
async def confirmed_order(client, authenticated_user, purchasable_product) -> ConfirmedOrderContext:
    root = purchasable_product.root
    product = root.step(ProductResult)
    buyer = authenticated_user.root.step(RegisterResult)
    created = await create_order(client, headers=bearer_headers(buyer), ...)
    paid = await pay_order(client, headers=bearer_headers(buyer), ...)
    return ConfirmedOrderContext(
        root=PipelineResult(steps=(*root.steps, paid)),
        product_ctx=purchasable_product,     # ✅ 持有子 Context
    )
```

这个方案被当前架构封死的原因：

1. **`*Context` 仅含 `ActionResult`**：`PurchasableProductContext` 如果声明 `shop_owner: ShopOwnerContext` 字段，就是在**嵌套 Context**——违反决策 3。
2. **Fixture 的依赖关系在 pytest 侧是合理的**（`confirmed_order` 依赖 `purchasable_product`），但**数据流跨了 `Context` 边界**——Context 作为 fixture 的数据容器，从依赖 fixture 流向依赖它的 fixture。
3. **替代方案是把嵌套逻辑放进 helper**，但这样 helper 就要返回含 Context 的数据结构，违反"helper 只返回 `*Result` / `PipelineResult`"的分层约定。

### 当前绕行方案：arrange_confirmed_order helper

当前实际做法是把链条收进 helper，fixture 仍然扁平：

```python
# tests/support/helpers.py
async def arrange_confirmed_order(
    client, *, shop_owner: PipelineResult, admin: PipelineResult,
    buyer_headers: dict[str, str], stock: int = 10, qty: int = 1,
) -> PipelineResult:
    arranged = await arrange_purchasable_product(
        client, shop_owner=shop_owner, admin=admin, stock=stock,
    )
    category = arranged.step(CategoryResult)
    product = arranged.step(ProductResult)
    if product.status_code != 201 or product.body is None:
        return PipelineResult(steps=(category, product))
    created = await create_order(client, headers=buyer_headers, ...)
    paid = await pay_order(client, headers=buyer_headers, ...)
    return PipelineResult(steps=(category, product, paid))
```

注意这个 helper 的签名：`shop_owner: PipelineResult`、`admin: PipelineResult`——这四个参数中的两个（`shop_owner` 和 `admin`）是**从 fixture 的 Context.root 中提取的**。fixture 在调 helper 之前，必须先持有上游 fixture 的 Context 并解包。**Fixture 事实上在承担依赖管理，只是没写在 pytest 的依赖参数里，而是写进了 helper 的实参传递中。**

当前架构在以下约束的交集中达到局部最优，但无法在不松开某个约束的前提下继续优化：

```
理论主张                          技术约束
──────────────────────────        ────────────────────────
fixture 不含业务逻辑              ActionResult 不做树
Context 不下沉到 helper           PipelineResult 扁平管理
fixture 应尽量薄                 *Context 仅含 ActionResult
                                 ↓
                         从零组装 ← 唯一剩下的方案
```

### 被封死的两条路径

| 理想方案 | 被什么封死 |
|----------|-----------|
| **Fixture 嵌套**：`confirmed_order` 依赖 `purchasable_product` fixture，自动获得其 Context | `*Context` 仅含 `ActionResult`，不支持 Context 嵌套；fixture 返回 Context 后无法"自动展开"给下游 |
| **ActionResult 树**：高层 helper 返回的结果自动包含所有历史子结果 | 复杂度预算不允许（胖对象、typing 膨胀、声明式丧失） |

### 实际效果

- **从零组装**：高层 fixture 需要手动传所有前置参数，从调用方角度看像是在重复写 Arrange 步骤。
- **Fixture 事实上在做依赖管理**：只是披着"helper 参数显式声明"的外衣，没有写成 fixture 依赖 fixture 的形式。
- **理论立场在守，实践上守不全**：当前 fixture 的行为（准备前置数据、传给下一层 helper）与 fixture 依赖所承担的职责等价，仅组织形式不同。

### 为何接受

1. **当前规模下没有实质性的维护负担**——ordering 域 5 个测试文件，从零组装的重复在可接受范围内。
2. **Typing 纪律为后续重构留了底牌**——所有 `PipelineResult`、`*Result`、`*Context` 都有完整类型注解，未来改数据流结构时有编译器辅助定位所有调用点。
3. **这是第三次重构后的第一次实战**——让架构在实际使用中沉淀一段时间，比在抽象中继续推演更有价值。

## 后续可能的演进方向

当以下信号出现时，应考虑重新评估当前约束：

- 从零组装在三到四个 domain 中重复出现，重复次数超过 50 次
- 多层 helper 调用链（深度 >= 4）开始频繁出现，显式传参的噪音超过收益
- 出现需要共享"半组装"状态的场景（如跨域复用某个中间步骤的 fixture）
- 团队规模变大（个人项目暂不适用）

届时可能的解法：

- **松开 Context 不下沉**：允许 fixture 持有其他 Context，但不作为 helper 参数传入
- **松开 ActionResult 扁平**：允许高层 Result 选择性引用子 Result（可选字段而非嵌套树）
- **引入 fixture 依赖**：同一 domain 内高频 fixture 可依赖底层 fixture，但保持"fixture 不写业务逻辑"的底线

## 事后识别：2026-07-20 讨论确认

### 识别到一个被忽视的约束

当前架构暗含了一个从未被明确声明的约束：**纯 HTTP 断言**——所有 Arrange 验证和状态断言都只通过 HTTP 响应体完成，不使用 DB 查询验证系统状态。

这个约束是导致从零组装和胖数据容器的根本原因：

- 因为只读 HTTP 响应，所以 Arrange 阶段需要 `assert status_code == 201` + `assert body is not None` 来确认前置条件已满足（DB 查询可以一步确认）
- 因为只读 HTTP 响应，所以跨步骤的数据（product_id、stock 等）必须在 `*Result.body` 中传递，无法在 Assert 阶段通过 `db_session.get()` 直接查
- 因为只读 HTTP 响应，所以 `PipelineResult` 退化为"所有历史数据的扁平链 + access_token 容器"

### 结论：放弃纯 HTTP 约束，引入 DB 查询

1. **Arrange 阶段**：创建完资源后，不需要从 HTTP 响应取 ID 并 assert body——DB 查询可以确认"数据确实落库了"。
2. **Assert 阶段**：状态验证（库存、订单状态）优先走 DB 查询，不依赖 HTTP 响应体携带额外字段。
3. **瘦数据容器**：`*Result.body` 只保留 API 本身的契约字段，不再作为"状态验证源"。最终 `PipelineResult` 可能简化为一个仅持有**非持久数据**（主要是 `access_token`）的轻量容器——类似 LangGraph 的 ToolRuntime 思想，只管理 DB 管不了的东西。

### 推演后的架构变化方向

| 当前 | 未来 |
|------|------|
| PipelineResult 管理所有步骤的 ActionResult | 简化为 AuthSession 或 TokenMap（仅持非持久状态）|
| `*Result.body.id` 传递到下一步 | DB 查询取 ID |
| Case Arrange 前 `assert status_code + body is not None` | 可大幅简化或移除 |
| `*Context(root: PipelineResult)` | Context 退化为非持久数据容器 |
| 从零组装 | 依赖层级可能自然减少 |

1. 先给少量测试加 DB 断言作为补充验证，不动基础设施
2. 确认 DB 断言模式有效
3. 逐步缩减 `*Result` 范围：先砍 ShopResult、CategoryResult 等 DB 可查的
4. 最后只留 `LoginResult` / `RegisterResult`（含 access_token）
5. 重新设计 Context 为纯非持久数据容器
