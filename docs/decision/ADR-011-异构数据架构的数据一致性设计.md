# ADR-011：异构数据架构的数据一致性设计——单一事实源、派生数据与逻辑外键

- **状态**：已采纳（`ai-rag-acl-index` propose 阶段定稿）
- **日期**：2026-08-18
- **背景**：`infra-ai-pgvector`（Change 1）引入 PG 作为 AI 读库后，系统形成**异构数据架构**：MySQL 为业务写源（权威），PG 为 AI 读副本（派生）。Change 2（`ai-rag-acl-index`）设计商品语料索引时，遇到三类数据一致性问题：① 商品归属（shop_id）在 MediaAsset 冗余会导致跨店泄露（评审 5）；② `media_assets.product_id` 是否加 FK（评审 4）；③ 删除/清理路径的跨库一致性（评审 6）。本 ADR 固化异构架构下数据关联与一致性的通用原则，适用所有未来 MySQL→PG 同步场景。

## 决策

### 1. 单一事实源：任何业务属性只在权威库存一份

任何可变的业务属性（如商品归属 shop_id）**只在权威库（MySQL）存一份**；读副本或其它表需要该属性时，通过**引用**获取或作为**派生数据**重建。**禁止**在权威层冗余属性拷贝。

- 判据：一份可修改的真相 = 事实源；第二份拷贝 = 双事实源（漂移必然发生，检测只能事后拦截）。
- 推论：`MediaAsset` **不存 shop_id**——文档的归属从商品继承（product_id → products.shop_id）。

### 2. 引用 vs 拷贝：外键引用不制造双事实源

外键引用（如 `media_assets.product_id` → `products.id`）是**指路**，不复制任何商品属性——商品标识（主键）唯一且不变，不存在"第二个真相"。**属性拷贝**（如冗余 shop_id）才是双事实源。

- 引用 = 通往单一事实源的方式；拷贝 = 制造第二个事实源。
- 引用正确性（写错 product_id）是脏数据问题，与双事实源（漂移）不同：前者可恢复（校验 + reindex 兜底），后者是结构性缺陷。

### 3. 派生数据：读副本内的冗余是缓存性质，不算法则事实源

读副本（PG）内的冗余列（如 `product_embedding_chunks.shop_id`）是**派生数据**——为检索/过滤优化而从权威源复制的缓存字段。判据：

- 事实源 = 权威可修改的那份；派生数据 = 从权威源生成、靠**重建**（reindex）保持一致。
- 缓存冗余是正常架构（与 Redis 缓存同性质）；一致性机制 = 重建，不靠数据库约束。

### 4. 逻辑外键：跨库关联用同值 UUID 列，无物理约束

MySQL 与 PG 是独立数据库，**跨库无法建立 FK、无法做数据库级校验、无法做跨库事务**。跨库关联用**同值 UUID 列**（逻辑外键）：

- `product_embedding_chunks.product_id ↔ products.id`、`shop_id ↔ shops.id`、`document_id ↔ media_assets.id` 均为逻辑外键。
- 一致性维护完全靠应用层：reindex 拉取 + 对比源状态 + orphan 扫描。

### 5. 外键约束判据：价值 = 被引用方的删除风险

是否加物理 FK（单库内）由**被引用方的生命周期**决定：

- 被引用方**存在删除路径**（如 `media_assets` 被 products/shops/users 引用，media 可删除）→ FK + 引用检查（`count_references` → 409）保护删除。
- 被引用方**无删除路径**（如 `products` 无 DELETE /products，只有下架）→ FK 价值 ≈ 0（悬空不会因删除发生），只剩阻塞代价 → **不加 FK**，完整性由应用层校验承担。
- 本项目既有先例：media 删除前的引用检查是应用层实现，非 FK 强制。

### 6. 校验分层：每层只校验能力范围内的完整性

校验**沿数据消费方向流动**，每层只做不构成新依赖的校验：

- media 域：仅 UUID **格式校验**（本域能力，零跨域依赖）；**不做** product 存在性校验（反向读 catalog 会成环——catalog→media 依赖已存在）。
- ai 域（数据消费者）：**存在性/归属校验**（reindex 时经 catalog 比对，无效 product_id 的文档跳过并记日志）——既是唯一无环位置，又是 ACL 正确性前置（幽灵 product_id 无法确定 shop_id，唯一安全行为是跳过）。

### 7. 重建机制：reindex 是派生数据的一致性机制

派生数据（PG 向量表）的一致性机制 = **reindex**（delete-then-insert per document，对比源状态清理失效行）。MVP 手动/CI 触发；Outbox 事件驱动（ADR-009）落地后，触发方式升级为事件同步，**原则不变**。

## 否决的观点

| 观点 | 否决理由 |
|------|---------|
| MediaAsset 冗余 shop_id（ACL 键不靠 join） | 双事实源：与 products.shop_id 漂移即跨店泄露（ADR-007 安全边界）；"ACL 键不靠 join"只对 chunk（派生数据）成立，不对权威层成立 |
| `media_assets.product_id` 加物理 FK | 价值 ≈ 0（products 无删除路径），代价真实（阻塞未来 DELETE /products 演进） |
| media 反向调 catalog 校验 product 存在 | catalog→media 依赖已存在，反向即成环 |
| 业务域（catalog/media）回调 ai 清理 chunk | 业务域依赖 ai = 循环依赖 + 违反 CLAUDE.md 跨域纪律；清理收敛到 ai 域 reindex |
| 跨库一致性靠事务/双写 | 异构跨库无分布式事务；双写需自行保证原子性，成本高于 reindex 重建 |

## 后果

### 正面

- 消除双事实源：权威层属性单份，跨店泄露在结构上不可能。
- 业务域零 ai 依赖：依赖方向 ai→业务域单向，无环（当前代码库无业务域 import ai）。
- ACL 安全边界：chunk.shop_id 永远来自权威源（商品归属），引用错误最坏 = 漏索引（可恢复），不触碰隔离边界。

### 负面 / 限制

- stale 窗口：下架/删附件后至下次 reindex 前，检索可能短暂返回失效内容——文档化接受。
- 引用正确性无法完全自动验证：系统只能验证"引用存在"，无法验证"引用语义正确"（文档是否真属于该商品）——上传者责任。
- 派生数据一致性靠重建，非实时：MVP 接受，Outbox 后置。

## 演进路径

```text
当前（ai-rag-acl-index）:
  逻辑外键 + reindex 重建 + 校验分层（MVP 手动触发）

```
