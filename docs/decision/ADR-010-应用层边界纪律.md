# ADR-010：应用层边界纪律——组合根装配自由、副作用归 service、current-object 解析判据

- **状态**：已采纳（`refactor-app-layer-discipline` propose 阶段定稿；apply 时随 rule / architecture 落地）
- **日期**：2026-08-10
- **背景**：`refactor-app-layer-boundaries` 已清除 deps 四反模式（① 建 schema ② 跨域 ③ 跨域两步 ④ 上帝 service），但应用层规范未成文。本 change propose 过程中，原定"service 双形态（返 schema + 返 ORM getter 供 deps）"被**归谬推理**推翻——service 为 deps 造公开 ORM getter 是依赖注入方向的反转（反向倒灌），并埋下"跨域调用方把 service 当依赖提供器"的破窗。本 ADR 定稿应用层边界纪律：**组合根装配自由、副作用归 service、current-object 解析按"是否携带业务"分判**。

## 决策

### 1. service 公开方法 = schema 出口 + 业务方法（推翻"返 ORM 双形态"）

- service 公开方法仅两类：**返 schema**（跨域/响应，`get_my_shop` → `ShopResponse`）与**业务方法**（含业务读，`expire_if_needed`；`get_order_response(order)` 收已鉴权实体后内部懒释放 + items 数据准备 + 映射）。
- **不为 deps 提供返 ORM 的公开 getter**：`get_shop_or_404` 不新增；`get_order_or_404` 私有化 `_get_order_or_404`。
- 命名：`get_*` 公开（schema 出口 / 业务方法）、`_to_*` 私有映射、`_get_<entity>_or_404` 私有 helper。

### 2. current-object 解析判据：纯读→仓储 / 业务读→service / 跨域→service

| 类 | 解析性质 | 走哪 | 实例 |
|----|---------|------|------|
| 纯读解析 | 查实体 + 404 + 状态无关归属比较，无副作用 | 本域仓储直读（组合根） | `get_current_shop` / `get_current_product` / `get_current_cart_item` / `get_current_checkout_batch` / `get_current_user` |
| 业务读 | 解析伴随业务副作用 | deps 纯定位；service 读方法内完成业务 | `get_current_order`（懒释放/items 归 `get_order_response`） |
| 跨域解析 | 本域 deps 解析别域实体 | 对方 service 公开方法（schema） | `get_current_support_shop`（转发 `get_my_shop_context`） |

**鉴权切分**：状态无关归属比较（buyer/owner/user）→ deps（身份解析）；状态依赖校验（过期 / 可支付 / 店铺关闭）→ service 方法内（业务授权）。

### 3. 铁律条文（落 `.cursor/rules/app-layer-discipline.mdc` 与 `docs/architecture.md` §4）

- **deps**：装配自由（吃本域仓储任意组合；跨域只经对方 service 公开方法，"本域"是硬边界）；无副作用（不触发写、不建 schema、不做业务数据准备；只做注入 + 存在性定位 404 + 状态无关归属比较）。
- **service**：一切业务动作归 service（含读路径状态迁移、数据准备、跨域业务调用）；方法自含业务完整性（不依赖调用方/deps 先触发业务前置，cancel 补 expire 为模板）；**被跨模块/跨域消费的方法不得是私有，且自含完整性前置或显式参数传入**（`_create_order_core` 跨模块调用是反例）。
- **配套**：router 拿 deps 实体必须传 service 方法、不得直接序列化（deps 只保证"存在 + 有权"，不保证"新鲜 + 完整"）；归属失败统一 404（不泄漏存在性）、状态失败 409/422；lint 边界（跨域白名单 / `get_current_*` 消费方 / `_*` 私有名 = AST 强制；状态无关 vs 状态依赖 = review 判据，AST 机械不了）。

## 归谬推理：为什么不该让 deps 承担 service 的任务

**前提**（被推翻的旧规则）："deps 禁止直吃仓储" → current-object deps 拿实体只能经 service。

**链条**：
1. service 被迫暴露公开 ORM getter（`get_shop_or_404` / `get_order_or_404`）供 deps 消费——"service 双形态"。
2. 这些 getter 是纯透传（`repo.get_by_owner_user_id` + 404），**零业务价值**——service 存在只为满足 deps 装配，依赖注入方向反转（本应是 deps 装配 service 的依赖，变成 service 为 deps 造方法，即"反向倒灌"）。
3. **归谬**：service 一旦有公开 ORM getter，跨域调用方为"获取依赖项"就直接跨域调 `service.get_xxx`——反模式③（跨域两步）的种子复燃，service 边界被侵蚀成"依赖提供器"。
4. **结论**：前提为假。组合根本义是装配自由——本域仓储是 deps 装配出的合法组件，纯读解析由组合根完成；service 只拥有业务逻辑 + schema 出口，不管依赖项怎么来。

**物归原主**：懒释放等副作用从不是 deps 的职责，是"deps 禁仓储"把组合根的解析拽进 service、D 轮又把业务塞回 service 却留了尾巴（deps 还在触发 `expire_if_needed`）。本决策把尾巴剪掉：deps 纯定位，副作用回 service。**行为不变只是结果，原则才是原因**——`cancel_order` 补 self-expire 保留 409，是"方法自含业务完整性"这一原则的产物，不是对行为约束的妥协。

## 为什么 current-object 不能跨域

**滑坡论证（破窗效应）**：跨域 current-object deps（如 support router 用 catalog `get_current_shop`）让 deps 变成域公共面 → 诱发 deps 建 schema（反模式①）→ deps 交互网在 service 边界外绕出 → 小违规累积成架构侵蚀。跨域协作只走 **service + schema**；current-object deps 本域独用；跨域实体解析经对方 service 公开方法返 schema（上表"跨域解析"类）。

## 否决的观点

| 观点 | 否决理由 |
|------|---------|
| service 双形态（返 ORM getter 供 deps） | 反向倒灌：组合根职责被 service 代做，埋"跨域调 service 拿 ORM"破窗（见归谬推理） |
| deps 禁仓储，一律经 service | 组合根本义被破坏；产出零业务价值透传 getter；正是其必然推论把 service 拉下水 |
| update_product B 方案（router 拿 Shop → service 查归属） | 鉴权留在 service，不符合"鉴权进 deps" |
| 过期订单取消改 200（不动 cancel_order） | 否决，选 self-expire 保 409——"方法自含业务完整性"是原则而非妥协 |
| support 店主 deps 把 ShopResponse 转 ShopContext | deps 建 schema = 反模式①；应新增 `get_my_shop_context` service 方法，deps 只转发 |
| 消灭懒释放（后台任务统一释放） | 暂缓为 follow-up（行为变更更大）；本 change 只做"触发点归 service" |

## 后果

### 正面

- service 公开面收窄：schema 出口 + 业务方法，无"为 deps 而造"的 getter。
- current-object 解析判据可执行（纯读 / 业务读 / 跨域），消灭"deps 禁仓储"的模糊地带与"违规"误判（`get_current_shop` 直吃仓储改合规）。
- router 不直接序列化 + 可达性子句，堵住反模式③复燃与鉴权旁路。

### 负面 / 限制

- deps 返回实体不保证"新鲜 + 完整"（过期订单可能原样返回）——以"router 不得直接序列化"硬约束兜底。
- 状态无关 vs 状态依赖是 review 判据，AST 无法机械强制（lint 边界见决策 3）。
- 改造范围略增：`get_my_shop_context` 新增、`_create_order_core` 私有访问收编。
