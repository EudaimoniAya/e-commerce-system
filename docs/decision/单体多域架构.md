# ADR-001：采用简易版单体多域（Modular Monolith）架构

- **状态**：已采纳
- **日期**：2026-07-08
- **背景**：个人 AI 赋能电商项目，预估电商部分约 3000 行、全项目约 1 万行。需要在快速迭代（可能每天改库、加功能）与工程化（SDD + TDD + CI）之间取得平衡，并为后期 AI 能力叠加和可能的微服务拆分预留结构。

## 决策

采用 **简易版单体多域（战略型 DDD）** 架构：

- 按 **限界上下文** 纵切为独立域目录（`user/`、`catalog/`、`ordering/` 等）
- 每个域内部保持 router → service → repository → model 分层
- 跨域协作 **仅通过对方 service 层 + Pydantic schema（DTO）**，禁止跨域 import ORM 或 repository
- AI 能力作为 **邻接域**（`ai/`）与业务域并列，通过 Tool 调用业务 service
- 共享技术设施放入 `infra/`，不建立「基类业务域」

不采用传统按技术层横切的分层单体（`models/`、`repos/`、`services/`、`api/` 全局分包）。

## 理由

### 1. 开发体验：目录即业务，随手可及

传统分层架构按 **技术层** 分包（`schemas/`、`routers/`、`repositories/`、`models/`、`core/`），开发一个功能时需要在多个按字母排列的目录间来回跳转，无法按开发顺序组织文件，且容易同时打开大量文件，影响专注度。

单体多域按 **业务域** 纵切，一个域内的 router、service、repository、model、schemas **聚在同一目录**：

```text
catalog/
  router.py      ← 开发商品功能时，只在这个目录里工作
  service.py
  repository.py
  models.py
  schemas.py
```

目录结构直接反映业务结构，降低认知负担，对个人项目的日常开发体验有明显改善。

### 2. 快速迭代：避免涟漪修改

项目处于快速开发阶段，可能每天修改数据库、增加新功能（购物车、收藏、浏览等）。传统分层 + 共享 ORM 模式下：

- 修改 `Product` ORM 的一个字段，所有 import 了该 model 的 service、repo、AI sync 脚本都可能需要联动修改
- 跨域调用路径无物理约束，容易从各种位置 import 依赖，改一处碎一片
- AI 辅助开发时，缺少 import 纪律的代码结构更容易被「走捷径」的生成代码污染

单体多域通过 **service 层作为域的唯一对外接口**：

- **导入方便**：跨域只需 `from catalog.service import get_product`，不需要知道 catalog 内部有哪些 repo 或 model
- **修改方便**：catalog 内部重构（改表、改 repo、改 ORM 关系）不影响 ordering，只要 service 接口和 schema 不变
- **约束 AI 生成**：OpenSpec spec 可明确写「不得 import catalog.models」，TDD 可验证边界

### 3. 与 AI 二维架构同构，便于未来拆分

本项目的 AI 架构设计遵循同一依赖原则：

| 层级 | 业务域间 | AI 与业务 |
|------|----------|-----------|
| 不直连底层 | 不 import 对方 ORM/repo | Tool 不直连数据库 |
| 公开接口 | service + schema | Tool → 业务 service |
| 并列扩展 | 新域 = 新目录 | 新 AI 功能 = ai/ 下新子模块 |
| 路由编排 | HTTP 路由 | + 意图识别 / AI vs 传统分流 |

业务域间的「只走 service、不碰底层」与 AI 的「Tool 只调 service、不碰 repo」**同构**。这意味着：

- 现在练好的依赖纪律，直接适用于 AI 集成
- 若未来 AI 拆为独立微服务，Tool 从函数调用变为 HTTP client，业务 service 签名可保持不变
- 若未来某业务域（如 catalog）拆出，ordering 侧从函数调用变为 HTTP client，结构变化最小

此做法与中型电商企业内部常见的 **模块化单体** 实践一致：部署上是单体，逻辑上多上下文，按域分包而非按层分包。

## 域间协作细则

### 依赖规则

```text
✓ ordering.service → catalog.service.get_product() → ProductSummary
✓ ai.tools → catalog.service / ordering.service
✓ 各域内部 → 本域 repository → 本域 ORM

✗ ordering → catalog.models.Product
✗ ordering → catalog.repository
✗ catalog → ai（任何模块）
```

### SQLAlchemy relationship 使用范围

- **域内**： freely 使用 relationship（如 `Order.items → OrderItem`）
- **跨域**：只存 FK 字段（如 `order.user_id`），不声明跨域 relationship；需要关联数据时调对方 service 或在本域 `queries.py` 做只读 JOIN

### 读路径 pragmatic 折中

写路径严格走 service；读路径（列表页需要 user_name 等跨域字段）允许在本域 queries 中 JOIN，但返回 schema 而非 foreign ORM 对象。

## 不做什么（本决策范围内）

- **不上战术 DDD 全套**：不使用聚合根、领域事件、值对象等模式（Outbox 在 AI 同步阶段再引入）
- **不建 Port/Adapter 抽象层**：小项目直接函数调用，不定义 Protocol 接口（除非测试需要 mock）
- **不建「基类业务域」**：代码复用放在 `infra/` 和可选的 `shared/`，业务复用走 service 调用
- **不为 imaginary 性能优化**：单体同进程跨域 service 调用的开销可忽略，优先边界清晰

## 域划分（当前与近期）

| 域 | 包名 | 阶段 |
|----|------|------|
| 用户 / 账户 | `user/` | MVP |
| 商品目录 | `catalog/` | MVP |
| 订单 / 购物车 | `ordering/` | MVP + Phase 2 购物车 |
| 用户行为（收藏 / 浏览） | `engagement/` | Phase 2 |
| AI 能力 | `ai/` | AI 阶段 |

## 替代方案及否决理由

| 方案 | 否决理由 |
|------|----------|
| 传统分层单体 | 开发体验差（目录按字母不按业务）；共享 ORM 导致涟漪修改；与 AI Tool 架构不同构 |
| 完整六边形架构 | Port/Adapter 全套对个人 3000 行项目过度抽象，AI 辅助开发易生成冗余接口 |
| 战术 DDD 全套 | 聚合根、领域事件、值对象对 MVP 过重；战略纵切已足够 |
| 直接微服务 | 1 万行规模无必要；模块化单体保留拆分选项但不过早支付分布式成本 |

## 影响

- 新建业务功能时，先确定归属哪个域，再在域目录内按 router → service → repo → model 实现
- 跨域需求通过目标域 service 接口满足，新增接口时同步定义 schema
- OpenSpec change 的 spec 中应明确域边界约束
- `.cursor/rules/` 中应包含跨域 import 禁止规则
