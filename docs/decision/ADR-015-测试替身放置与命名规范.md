# ADR-015：测试替身放置与命名规范

- **状态**：已采纳
- **日期**：2026-08-26
- **背景**：change3（`ai-support-agent`）合并后，AI 域 12 个测试文件暴露测试替身（代替真实依赖的假对象）三重混乱——命名与角色脱钩（`_Fake*` 一个前缀装了四种不同角色）、放置无判据（测试内散落/硬编码进业务代码/环境变量劫持三种形态并存）、与产品假实现重复（`_FakeLLM` 和产品里的 `MockLLMClient` 功能一样写了两遍）。诊断发现与 Meszaros 在 2000 年代初遇到的"所有替身都叫 mock"的问题同构。本 ADR 定测试替身的**放置**（放哪）、**命名**（叫什么）、**反模式**（不许什么）；长期规范落 `.cursor/rules/test-doubles.mdc`，一次性迁移动作归对应 change。

## 关键决策

### 决策 1：放置连续谱（五档 + 三个判断问题）

替身放哪是一个连续谱，从测试侧到生产侧共五档（档 = 摆放方式）：

| 档 | 摆放方式 | 评价 |
|---|---|---|
| 1 | 测试自行全部装配（替身全在 tests/） | ⚠️ 合法但冗余：与产品假实现功能重复，优先复用 |
| 2 | **双模式**：单组件配置字段 + 装配层分派 | ✅ **首选**：显式、可验证、粒度细；须带快速失败 |
| 3 | 环境级连坐（一个环境变量切换一批假实现） | ✅ 合法：假实现多时省事，但选择隐式 |
| 4 | 生产侧硬编码假实现（无协议无抽象） | ❌ 不规范：耦合写死，换真实现要改业务代码 |
| 5 | 测试劫持生产行为（业务代码里的测试专用环境变量分支） | ❌ 反模式：测试验证的行为分支生产不存在 |

**三个判断问题**：
1. 依赖能否在本地跑起来？（能 → 测试用真实依赖，零替身；不能 → 问 2）
2. 除了测试，还有谁需要假实现？（选了"开箱即用"→ 档 2/3；没选 → 档 1）——⚠️ **CI 需要假实现不算"还有谁需要"**，CI 就是跑测试的地方
3. 假实现怎么切换？（配置字段/环境变量 → 合法；硬编码 → 升级；业务内环境分支 → 反模式）

**档 2 vs 档 3**：会只想替换单个组件（粒度细）→ 档 2；想"假就全假"且假实现 ≥5 个 → 档 3。两档都必须快速失败（生产环境选中假实现启动即报错）。

### 决策 2：Meszaros 五类命名（前缀即角色）

判断替身属于哪一类：**有没有"自己的逻辑"？** → 有 → Fake；没有 → **测试跑完验证什么？** → 验证结果 → Stub；验证调用 → Spy（事后查）/ Mock（预先声明）；什么都不验证 → Dummy。

- 命名：`_Stub*`（喂数据）/ `_Spy*`（查调用记录）/ `_Fake*`（有逻辑）/ `_Never*`（不许碰，即"期望绝不调用"的 Mock 特例）
- **使用频率**：Fake 是主力（~90%），Stub/Spy 常用，Dummy/Mock 走替代路径（Dummy 配 `_Never*`；Mock 交给 unittest.mock 的 `assert_called_*`，手写不写）
- **产品侧假实现统一 `Fake*` 命名，禁用 `Mock*`**——全库 `MockLLMClient`、`MockEmbedder`、`MockSmsProvider` 实际都是 Fake（有自己逻辑的假实现），"Mock"一词仅指 unittest.mock 框架工具与 `_Never*`
- **下划线即文件内私有**：带 `_` = 只在该测试文件用；共享替身不带 `_` 用全名

### 决策 3：反模式禁令（写死）

1. **测试劫持生产行为**：业务代码出现"测试"语义（`if is_test` / 测试专用环境变量分支 / 为测试改 TTL/限额）→ 反模式。实证：git `128c555` 已清理订单 TTL 的环境变量分支，替代是测试侧回拨数据（`backdate_order_expires_at`）
2. **硬编码假实现**：业务代码直接调假实现（假短信的 `send` 写死在业务函数）→ 升级为协议 + 构造注入/配置切换
3. **环境分支的理由判据**：环境分支的理由是"环境本身就该不同"（日志格式、DEBUG、数据库地址）还是"为了测试"（劫持）？看理由，不看形态

### 决策 4：复用优先与归属

1. **测试要替身，先看产品侧有没有现成假实现**（档 2 假实现）——够用就复用（`Fake*Client(output=...)` 即可编程输出），不够再自造（`AsyncMock(wraps=...)` 增强）
2. **测试工具放哪，跟着被测代码的域走**：跨域通用 → `tests/testkit/`；域内专用 → `tests/<域>/testkit/`（AI 域替身进 `tests/ai/testkit/`）
3. **共享判定**：被 ≥2 个测试文件用才共享，单文件用留文件内

### 决策 5：规范与迁移分离

长期规范文件（mdc/ADR）只放"约束以后怎么写"；一次性迁移动作（改名/删除/升级）归对应 change 的迁移清单——迁移完成即失效，写进规范会变成过期信息误导 AI。

## 关键权衡记录

- **档 2 vs 档 3**：粒度需求 × 组件数量。真实项目两者并存（Django 的邮件后端配置是档 2，Spring 的 `@Profile` 是档 3）
- **"开箱即用"是可选项**：不配外部凭据也能跑是产品决策不是必然——选它才需要生产侧假实现；不选（所有环境配凭据）假实现全在测试侧
- **五类完整 vs 使用频率**：分类学完整保留（用于识别现有代码实际是哪一类），使用规则按项目实际频率分主次，避免每类都造
- **替身 vs 假实现 vs 测试环境**：判断看角色不是看真假——测试库（真实 PostgreSQL 的独立实例）不是替身；生产侧假实现不叫替身叫生产组件
