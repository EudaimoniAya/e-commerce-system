# ADR-007：多租户扩展——设计与暂缓计划

- **状态**：已采纳（暂缓实现）
- **日期**：2026-07-30
- **背景**：在完成 `user-phone-auth` 后，曾规划 `merchant-tenant` change，引入 `Merchant`、`MerchantMember` 组织层，将 `shops.owner_user_id` 迁移为 `shops.merchant_id`，以支持多人协作（客服 operator、组织级 RAG/inbox）。经架构讨论与项目目标对齐后，决定 **当前阶段不实现** 该 change，改以最小电商底座支撑 AI 演示。

## 背景与问题

### 当前模型（截至本 ADR）

```text
User ──owner_user_id (UNIQUE)──▶ Shop ──shop_id──▶ Product
  │                                  │
  └── buyer_user_id ──────────────── Order / Cart
```

- 身份锚点：`users.id`（UUID），JWT `sub` 指向用户。
- 平台运营：`users.is_admin` → `require_admin`（与商家无关）。
- 店主：`shops.owner_user_id` UNIQUE，**1 User : 1 Shop**。
- 商家侧授权：`catalog.deps.get_current_shop` 查 `owner_user_id`；ordering 卖家路径、禁自购均绑定店主 user。

该模型在 **单人开店 MVP** 下合理，与 `catalog-shop` change 的交付范围一致。

### 多租户目标模型（已评估、未实现）

```text
User ──MerchantMember(role)──▶ Merchant ──merchant_id──▶ Shop
```

- **User**：登录身份，不变。
- **Merchant**：组织/租户壳，不直接等于某个 User。
- **MerchantMember**：`user_id + merchant_id + role`（owner / operator 等）。
- **Shop**：归属 `merchant_id`；商品、订单仍主要经 `shop_id` 隔离。

该模型与电商 SaaS（Shopify、有赞等）常见 **Org + Membership** 模式一致，可解决「仅店主能操作商家侧能力、客服无挂载点」的问题。

### 触发重新评估的直接原因

计划中的 **店铺智能客服（RAG + 对话框）** 若绑定 `user_id` 或仅 `owner_user_id`，则组织内客服、运营无法共用 inbox 与知识库。由此引发是否立即实施 `merchant-tenant` 的讨论。

### 项目约束（决策输入）

| 约束 | 说明 |
|------|------|
| 无真实用户、不上线 | 无需生产级 multi-tenant 迁移与 backfill 运维 |
| 面试作品集 | 信息密度应集中在 **AI 域**（RAG、Agent、Tool、对话闭环） |
| 电商底座为 AI 服务 | 底座应 **最小改动** 支撑演示 |
| OpenSpec 垂直切片 | 不创建无实现计划的活跃 change |

## 决策

**AI 演示阶段暂缓 `merchant-tenant` 实现**；维持现有 `owner_user_id + shop_id` 模型，并按以下约定扩展 AI 相关能力：

1. **对话（Conversation / Message）** 与 **RAG 语料/向量** 在演示阶段以 **`shop_id`** 为隔离键（metadata 过滤）；不从属于某个 User。
2. **商家侧 B 端操作**（inbox、RAG 配置、人工回复）仍通过 **`get_current_shop` → `owner_user_id`** 鉴权；演示时 **店主账号** 兼客服与 AI 配置者。
3. **不引入** `merchants`、`merchant_members` 表及成员邀请 API；**不在** `openspec/changes/` 创建 `merchant-tenant` change。
4. **后续 AI 垂直切片** 按 **`support-conversations` → `ai-support-agent`** 顺序交付（`feature/*` 分支），不依赖本 ADR 所暂缓的组织层 migration。
5. 在 **`catalog.deps.get_current_shop`** 保留 **一处** 文档级指向本 ADR，标明组织层为可扩展项（见「演进路径」）。

## 理由

### 演示闭环在现有模型下已足够

目标演示路径：

```text
买家 User → 店铺页发起对话（shop_id）
         → RAG Agent 检索该 shop 知识库 → 写入 AI Message
         → UI 提示「当前为 AI 客服」
         → 买家「转人工」→ handler_mode=human → 店主 inbox 人工回复
```

该路径 **不要求** `Merchant` / `MerchantMember`：

- 租户隔离：`shop_id` 即可区分不同店铺语料与会话。
- 人工客服：店主一人扮演即可；operator 角色与邀请流程在演示 story 中非必需。
- MVP 1 User : 1 Shop 与「只为体现 AI 逻辑、非还原完整 SaaS」的目标一致。

### 立即实施 multi-tenant 的成本与收益不匹配

| 若实施 merchant-tenant | 代价 |
|------------------------|------|
| 新表 + migration + backfill | 改动 catalog/ordering 授权链、禁自购语义、测试 fixture |
| `PurchasableProduct`、spec 大量 delta | 与 AI 演示主线争抢工期 |
| 面试叙事 | 底座迁移故事 **弱于** RAG + Agent + Tool 闭环 |

暂缓后，底座 **几乎零迁移**，AI change 可快速垂直切片。

### 保留演进文档而非删除讨论成果

多租户模型已评估为 **生产/SaaS 演进方向**；本 ADR 记录 **为何现在不做** 与 **将来怎么做**，避免后续重复讨论或误以为「当前设计错误」。

## 后果

### 接受的能力边界（演示阶段）

| 能力 | 状态 |
|------|------|
| 买家 ↔ 店铺 AI 客服（按 shop 隔离） | ✅ 计划通过 support + ai change 实现 |
| 转人工（店主回复） | ✅ |
| 多成员协作 inbox（operator 小刚） | ❌ 不支持；可口述演进 |
| 一 User 多 Merchant / 邀请成员 | ❌ 不支持 |
| 组织级 `merchant_id` 隔离 RAG | ❌ 暂缓；演示用 `shop_id` |
| 禁自购 | 仍为 `buyer == shop.owner_user_id`（单人店足够） |

### 代码与文档

- **不修改** `shops` 表结构及 `owner_user_id` 语义。
- **不新增** merchant 域包。
- **`get_current_shop`** docstring 指向本 ADR，作为唯一代码内扩展点提示。

### 与平台 RBAC 的关系

- **`is_admin`**：平台运营（如 `POST /categories`），与商家组织无关；见 ADR-002、user-auth spec。
- **商家侧**：仍等价于「当前 user 是否为 shop 的 owner」；**不是**租户内 RBAC。

## 演进路径（未来若实施 SaaS / 多人协作）

建议独立 change：**`merchant-tenant`**（`feature/merchant-tenant`），边界参考如下（**非本阶段承诺**）：

### 表与迁移

```text
merchants
merchant_members   (user_id, merchant_id, role: owner | operator | ...)
shops.merchant_id
```

- Backfill：每个现有 shop → 创建 merchant + member(owner) + 更新 `merchant_id`。
- `owner_user_id`：**双写 → 停读 → 后续 change 删列**。
- 禁自购语义升级为：买家为该 shop 所属 merchant 的 **任意 member** → 403。

### 授权入口（避免散落 JOIN）

```text
merchant.service.get_membership(user_id, merchant_id)
merchant.service.resolve_shop_context(user_id)  → merchant_id, shop_id, role
```

### MVP 约束（届时仍可先 1:1 行为）

- 一 User 至多一个 owner Member；一 Merchant 至多一个 Shop。
- 无 active merchant 切换 API。
- `operator` role 可入表；邀请 API 单独 change。

### AI / 对话升级

| 演示阶段（本 ADR） | 演进后 |
|--------------------|--------|
| 对话 / RAG 隔离键 `shop_id` | 主隔离键 **`merchant_id`**；`shop_id` 作多店筛选 |
| 店主兼客服 | `MerchantMember.role=operator` 使用 inbox |
| `support-conversations` | 鉴权改走 `merchant.service` |

### 建议 change 顺序（演进时）

```text
merchant-tenant          ← 组织地基（曾在本 ADR 暂缓）
support-conversations    ← 对话主干（可先于 merchant 在演示阶段按 shop 实现）
ai-support-agent         ← RAG 赋能消息流
merchant-invite-members  ← 邀请 operator（可选更后）
```

## 替代方案

| 方案 | 结论 |
|------|------|
| 立即实现完整 merchant-tenant + operator | **否决**：scope 超出 AI 演示需要 |
| 在 `users` 上挂 `merchant_id`（1:1） | **否决**：无法 N:N；与已评估模型不一致 |
| 仅代码 TODO、无 ADR | **否决**：面试与后续协作缺少决策上下文 |
| 创建 OpenSpec `merchant-tenant` change 但不实现 | **否决**：change 长期活跃，规范维护成本高 |
