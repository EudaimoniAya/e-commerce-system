## 一、核心反模式 1：命名与角色脱钩（所有替身叫 `_Fake`，角色各不同）

### 错在哪

名字前缀不传达角色。`_Fake*` 一个前缀装了四种角色：Stub（固定返回）、Spy（记调用记录）、Fake（有自己逻辑）、纯数据载体。读测试时每个替身要猜三遍：它叫什么（命名）、它干嘛（类型）、它会不会炸（强度）。名字失去含义，review 无法讨论"这里为什么用 stub 不用 mock"，新人只能靠猜。

### 案例（change3 形态，已合并）

`tests/ai/test_intent_controller.py` 的 6 个替身，实际角色与名字全部对不上：

| 名字 | 实际角色 |
|---|---|
| `_FakeLLM` | Stub + Spy 混合（固定返回 JSON + 记调用记录） |
| `_FakePromptLoader` | Fake（按字典查模板 + 查不到报错，有自己的逻辑） |
| `_FakeGenerationLLM` | Spy（只记调用记录） |
| `_make_retrieve` | Spy（记参数） |
| `_FakeChunk` / `_FakeLoadedPrompt` | 纯数据载体 |

产品侧同病：`MockLLMClient`、`MockEmbedder`、`MockSmsProvider` 全是 **Fake**（有自己逻辑的假实现）却叫 `Mock`——"Mock"一词在项目里失去含义，还造成"AI 域是不是不用 Mock"的误读。

### 元教训

Meszaros 在 2000 年代初遇到完全同构的问题：所有替身都叫 mock，语义、用途、风险完全不同，名字失去意义——他因此写了《xUnit Test Patterns》提出五类分法。命名与角色脱钩的后果链：**阅读靠猜 → review 无法讨论 → AI 生成代码模仿现有模式、混乱自增强**（项目里全是 `_Fake*`，AI 写测试就继续生成 `_Fake*`，循环放大）。

### 判别法（记住这一句）

问：**名字能回答"这东西是干嘛的"吗？** 回答不了 = 脱钩。
可机械判定版：**前缀即角色**（`_Stub*` 喂数据 / `_Spy*` 查记录，含固定返回+记调用 / `_Fake*` 有真实行为且排除仅记录 / `_Never*` 零调用断言），产品侧假实现统一 `Fake*` 命名、禁用 `Mock*`。纯数据载体不进这些前缀。

### 应怎么做

命名规范（test-doubles.mdc 二节）：前缀即角色；测试侧按个数 Stub/Spy 最常见；Fake 是产品侧假实现的命名主力，测试侧只在有真实行为时用；混合（固定返回 + 记调用）归 Spy；纯数据载体不进五类；产品侧统一 `Fake*`。

## 二、核心反模式 2：放置无判据（散落 / 硬编码 / 环境劫持三种形态并存）

### 错在哪

没有"替身放哪"的判断标准，位置全靠感觉——同一个项目里同时存在三种形态：测试文件内散落（不可复用）、假实现硬编码进业务代码（换真实现要改业务代码）、甚至环境变量劫持（测试改生产行为，测试验证的行为分支生产不存在）。

### 案例

1. **测试内散落 + 与产品重复**：`_FakeLLM` 等 6 个类全在测试文件内，与产品里的 `MockLLMClient` 功能重复（同一件事写了两遍，~40 行冗余）。
2. **硬编码假实现（无协议无抽象）**：假短信的 `send` 写死在 `SmsOtpService.send_otp`（app/user/sms_service.py）——换真实短信网关要改业务代码。
3. **环境变量劫持（已清理）**：订单预留 TTL 的读取函数带 `ORDER_RESERVATION_TTL_SECONDS` 环境变量分支（git `128c555` 已删）——测试用环境变量把 TTL 调短，测的是"5 秒分支"，生产跑的是"900 秒分支"，**测试验证的行为生产不存在**。修复方式：测试侧直接回拨订单过期时间（`backdate_order_expires_at`），生产逻辑走正常路径。

### 应怎么做

放置连续谱五档（测试自装配 → 双模式配置切换 → 环境级连坐 → 硬编码 → 环境劫持）+ 三个判断问题（依赖能本地跑？→ 用真的；选开箱即用？→ 档 2/3 配置切换；没选 → 档 1，此时档 1 不是冗余）。选了开箱即用时档 2 优于档 3；档 4 硬编码、档 5 环境劫持写死为反模式。

## 三、元教训：规范与迁移分离（一次性动作不进长期规范）

### 错在哪

把"一次性迁移动作"（改名、删除、升级）写进长期规范文件。迁移完成后这些内容变成过期信息——AI 读到会困惑（"MockLLMClient 实际是 Fake"——可它已经叫 FakeLLMClient 了）。

### 判别法

问自己：**这个约束一年后还有效吗？** 有效 → 规范（mdc/ADR）；失效（因为会被改完）→ change 的迁移清单。

### 应怎么做

规范文件只放"约束以后怎么写"；迁移动作归 change。test-doubles.mdc 文件头已写入此约束。

## 迁移对照（change3 形态 → 规范形态）

| 维度 | change3（已合并，混乱） | 规范形态（待落地） |
|---|---|---|
| 命名 | `_Fake*` 装四种角色、`Mock*` 装 Fake | 前缀即角色；产品侧统一 `Fake*`；测试侧 Stub/Spy 按个数最常见 |
| 放置 | 散落测试文件 / 硬编码进业务 / 环境劫持并存 | 放置连续谱五档 + 三个判断问题；没选开箱即用 → 档 1；选了才档 2 优于档 3 |
| 复用 | `_FakeLLM` ≈ 产品 `MockLLMClient` 重复 | 测试先复用产品侧假实现，不够再自造 |
| 归属 | 替身全在测试文件内 | 跨域通用 → `tests/testkit/`；域内专用 → `tests/<域>/testkit/` |
| 反模式 | 硬编码（短信）、环境劫持（TTL，已清理） | 两条写死为禁令 |
| 规范载体 | 无 | test-doubles.mdc（长期）+ change `refactor-ai-test-doubles`（迁移） |

| 现名 | 实际角色 | 改后 |
|---|---|---|
| `_FakeLLM` | Stub + Spy（固定返回 + 记调用） | **删除**，注入产品侧 `FakeLLMClient` |
| `_FakeGenerationLLM` | Spy | **删除**，注入 `FakeLLMClient` |
| `_make_retrieve` | Spy（闭包记参数） | 可改名 `_spy_retrieve`；不必升格成类 |

| `_NeverGenerationLLM` | 零调用断言 | **保持** `_Never*` |
| `MockLLMClient` / `MockEmbedder` / `MockSmsProvider` | 产品侧 Fake | `FakeLLMClient` / `FakeEmbedder` / `FakeSmsProvider` |
