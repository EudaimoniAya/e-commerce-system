## 一、核心反模式：权宜伪装成约束（借 support 入口 → 注册表）

### 错在哪

把「实现选择的权宜」误认为「领域约束」，于是从它出发的推导链全部「不得已而为之」。单论一层（只看注册表本身）很容易觉得它合理——因为它在那一层里确实是被迫的。**被迫的源头在上一层（借入口这个选择），不在这一层。**

| 例子 | 真实约束（不可改/代价明确） | 权宜（其实是选择） | 被误认成 |
|---|---|---|---|
| 测试重构（PipelineResult） | 断言要覆盖行为 | assert 必须走 HTTP 全链路 | "HTTP 要携带所有 assert 信息" |
| 这次（注册表） | 业务域不得 import AI（ADR-013） | AI 必须借 support 入口赋能 | "AI 要走 support 才能赋能" |

### 案例（change3 形态，已合并）

```text
借 support 入口（权宜）→ support 需要 AI 能力但不得 import ai（真约束）
  → 注册表 register_buyer_turn_handler_factory（从权宜推出的"必然"）
  → handler_mode 状态机（支撑"一个入口两套模式"）
```

### 判别法（通用，记住这一句）

问：**「谁定的？现在改掉它，推导链还成立吗？」**
- 改掉「借 support 入口」→ 注册表整条链断裂 → 它是权宜
- 改掉「业务不能 import AI」→ 代价明确（对称网格、循环依赖）→ 真约束

### 应怎么做

接受一个架构机制前，先对它的推导链起点做分类（约束 / 权宜 / 猜测）。起点是权宜的推导链，结论是伪必然。梳理决策链必须沿因果链往上走：**每一层的「不得已」都是上一层「选择」的结果。**

## 二、AI 推导自洽不保证前提正确

### 错在哪

注册表设计「头头是道」——从「反向依赖 + deps 组合根」推出了必然，当时就接受了，像 change3 一样被迫接受了还未设计完全的决策，因为无法最开始就一次性定稿所有决策。

### 机制

AI（和任何人）的推导自洽，只能保证「从前提推出的结论正确」，**不能保证前提正确**。AI 生成架构设计时，会从既定前提（借 support 入口）推出无懈可击的结论，但没人质疑前提。

### 应怎么做

看 AI 生成的架构设计，「看懂」的定义不是「能复述推导」，是「能对推导链的每个前提做分类：约束 / 权宜 / 猜测」。只验证推导 = 接受前提，是看懂了一半。**从权宜推出的必然是伪必然。**

### 第二实例（2026-08-27：Cursor 提议「拍板 AI 写不写买家原文」）

**场景**：Cursor 会话「Explore AI 专用入口」（chat 模式），上下文 = 入口形态踩坑记录 + `controller.py` / `models.py` / `service.py` / `main.py` 四个文件。讨论到 AI 端点设计时，Cursor 提议：「需要拍板——AI 写不写买家原文」。

**事件脉络**：

```text
Cursor 的默认前提：AI 端点负责「一轮对话」
  → 推导：买家原文是这轮对话的一部分，自然归 AI 端点写
  → 提议：拍板「AI 写不写买家原文」（一个它认为需要决策的问题）

用户纠正（业务事实）：
  对话落库早由 POST /support/shops/{shop_id}/conversation/messages 实现
  （send_buyer_message 自动落库，author_role 区分角色）
  买家原文从来不由 AI 写——它只是「触发 AI 回合」的输入
  前端行为：人工模式只显示未读；客服模式时前端在买家发消息后触发 AI 端点调用

Cursor 承认：「你纠正得对：对话落库早就在 support 里，不是 AI 端点要去抢的活。
我上次把『AI 一轮』想成『连买家原文一起写』，那是另一条设计，不是你现在的产品。」
```

**机制拆解**：与第一实例（注册表设计）同构——**推导链自洽，前提错误**。Cursor 从「AI 端点 = 一轮对话」推出「买家原文归 AI 写」，每一步推导都成立，但前提来自**「合理的假设」而非「项目事实」**：它默认对话还没实现、AI 端点要包办整轮。项目越大、AI 读不全的上下文越多，这种「把假设当事实」越频繁。

**与第一实例的差异**：第一实例的前提错误是「权宜」——把实现选择（借入口）当成约束（AI 必须走 support）；第二实例的前提错误是「事实假设错误」——把「对话未实现」当成现状（实际已实现）。错误类型不同，机制相同：**AI 只验证推导，不验证前提；前提要由懂业务的人校准。**

**判别法（在 §一「约束/权宜/猜测」分类上补一类）**：

> AI 提议拍板「业务事实类」问题时，先问：**「这个事实在项目里已经存在了吗？」** ——查代码，不查推导。
> 买家原文落库不是约束、不是权宜、不是猜测，是**「已经实现」**——已实现的事实不需要拍板，只需要被查询。

**教训沉淀（三件事）**：

1. **AI 提议拍板任何「业务事实类」决策前，先查项目里有没有对应实现**——「对话落库在哪」在代码里一查就有，拍板前先 grep。
2. **掌控度是纠正的前提**：用户能纠正，是因为知道「买家消息由 support 落库、前端按模式触发 AI」——这是对项目付出心血换来的业务事实库。没有掌控，AI 的自洽推导无人校准；有掌控，AI 的每一条推导都能被事实检验。
3. **大项目里「AI 产出带回重审」是纪律不是选项**——AI 的失败模式不是逻辑差，是缺上下文时把假设当事实；项目越大越频繁。这正是 docs/temp 决策文档 + 用户亲自拍板（而非让 AI 自由发挥）的原因。

## 三、领域状态机 vs 实现状态机

### 错在哪

`handler_mode`（ai / human）状态机在需求早期反复摇摆——要不要默认 AI、何时转人工、谁触发切换，全定不下来。

### 区分

| | 领域状态机 | 实现状态机 |
|---|---|---|
| 状态空间由什么决定 | 业务本质 | 实现选择 |
| 例子 | 订单 pending→paid→shipped，删掉「已支付」概念就没了 | `handler_mode` 是「借 support 入口」的产物，删了 AI/人工照样工作（前端切换） |
| 稳定性 | 稳定，删不掉 | 可消解 |

**判据**：**状态空间改变时，业务语义变了吗？** 变了 → 领域；没变 → 实现，可以消解。

**关联**：「还没确定状态空间就建状态机 = 投机设计的变体」——状态机四要素（状态、转换条件、转换动作、默认态）在需求早期全是未知数，一次性定稿必然返工。能用无状态推导的，就别提前建状态机。

## 四、前端分流消掉状态机的机制（修复方向）

前端分别调用 AI 端点 / support 端点后，`handler_mode` 状态机整个消失：模式从「持久化状态」变成「端点选择」——瞬时决策、无残留、不需要提前枚举转换路径。

但转人工的**触发源**（τ 拒答、意图外）永远在 AI 内部，信号通过 AI 端点响应传给前端：

```text
AI 端点返回结构化结果：
  { type: "ai_answer",      reply: "..." }          → 前端下条消息继续发 AI 端点
  { type: "fallback_human", message: "转人工建议" }  → 前端下条消息切 support 端点
```

准确说法不是「前端负责所有分流」，而是**「入口选择在前端，拒识信号在 AI，信号经 HTTP 响应传递」**。本质：复杂度从「后端持久化状态机」（要提前设计所有切换路径）转移成「前端即时路由决策」（每个请求独立决定）——转移到**一个不需要提前设计的地方**。这不是复杂度消失，是复杂度搬家。

## 五、落库责任随入口形态转移（纪律反转）

change3 的纪律是「agent 不得回头调 support.service 落库，只交正文，support 自己写 author_role=ai」——那是借入口形态的产物。前端分流后，落库责任转移到 AI router。

精确分层（controller 纯净性不变）：

```text
controller/agent：纯逻辑（NLU→意图→生成文本）→ 不 import support，fake 可测 ✅ 纪律保留
AI router：接线层 → 调 controller 拿文本 + 调 support.service 落库（AI→业务合法方向）
```

**教训**：架构纪律（如「agent 不碰 support」）要标注它依赖的形态前提；形态变了，纪律随之反转，但**核心逻辑层的纯净性是不可动摇的那条**。

## 六、选型纪律（非踩坑，本次确立的原则）

- **面试叙事是需求**：项目是「面试剧场」，面试官是第二个消费者。「面试讲得出」和「功能跑通」一样是需求——这修正了标准 YAGNI 的计算（Celery 进项目是叙事需求，不是投机）。
- **选型矩阵（热度 × 重量）**：热门且轻 = 最佳；热门且重 = 可接受（MySQL、Celery，叙事买单）；冷门且重 = 拒绝（Milvus、K8s、gRPC）。
- **重工具可以进来演示，但永远不许扎根**：接入只做薄壳（任务壳 / 工厂），核心逻辑不依赖它，接缝可换实现（CLI ↔ Celery ↔ arq 同一批函数）。
