## 反模式索引


| #   | 反模式                                  | 典型位置                                 | 规范要求（摘要）                                                  |
| --- | ------------------------------------ | ------------------------------------ | --------------------------------------------------------- |
| 1   | test 文件内 HTTP helper + test 互 import | `_create_product`                    | helper 在 `tests/testkit/`；禁止 `from tests.*.test_* import` |
| 2   | helper 内 assert 成功状态码                | `_create_product` L51                | helper 如实返回 `*Result`；Case 或 fixture 边界 assert            |
| 3   | 组合 helper 返回 Context                 | `register_and_open_shop`             | orchestrator 返 `PipelineResult`；fixture 包 `*Context`      |

以下每个反模式：**1～2 个最突出案例** + 代码标注 + 正确方向（不展开全量文件清单）。

## 反模式 1：test 文件当 Support 层 + test 互 import

### 错在哪

- **Case 层**（`test_*.py`）混入了本应在 **Support** 的 HTTP 编排逻辑。
- 其他 test 文件 **import 另一个 test 模块**，测试文件变成「共享库」，pytest 收集顺序一变就容易踩坑。
- AI/人工会在「写 test helper」和「写 support helper」之间随机选边。

### 案例 A：helper 定义在 test 文件

`tests/catalog/test_create_product.py`：

```python
async def _create_product(
    client,                                    # ❌ 无类型注解
    admin_auth_headers: AdminAuthContext,
    shop_owner: ShopOwnerContext,
    *,
    is_published: bool = False,
    category_id: str | None = None,
) -> ProductResponse:                           # ❌ 返 domain schema，不是 ProductResult
    if category_id is None:
        category_id = await _create_category_for_product(...)  # ❌ 嵌套 test helper
    ...
    response = await client.post("/products", ...)
    assert response.status_code == 201          # ❌ 见反模式 2
    return ProductResponse.model_validate(...)
```

同一文件里的 **Case** 本应测 `POST /products`，却与 helper **重复实现** POST 逻辑（L73–77 又一次 `client.post`），Arrange/Act 边界模糊。

### 案例 B：test 互 import（最恶劣）

`tests/catalog/test_public_products.py`（被测是 **GET /products**，Act 应该是 `client.get`）：

```python
from tests.catalog.test_create_product import _create_product   # ❌ test 依赖 test

async def test_get_public_products_returns_only_published_active(...):
    published = await _create_product(client, admin_auth_headers, shop_owner, ...)
    await _create_product(...)
    response = await client.get("/products")    # Act 在这里，但 Arrange 来自另一个 test 文件
```

同类 import 还出现在：`test_my_products.py`、`test_update_product.py`。

### 应怎么做

- `create_product` → `tests/testkit/helper/catalog.py`，返回 `ProductResult`，不 assert 201。
- Arrange 在 Case 或 support 显式调用；**禁止** `from tests.catalog.test_* import ...`（CI grep 拦截）。

## 反模式 2：helper 内 assert 成功（替 Case 判定）

### 错在哪

helper 假定 **只能走 happy path**。一旦 API 返回 422/404，helper 直接 `AssertionError`，Case 拿不到 `*Result` 做负向断言，**无法复用同一条 HTTP 路径**。

### 案例：`_create_product` 与 `_create_category_for_product`

```python
async def _create_category_for_product(client, admin_auth_headers) -> str:
    assert admin_auth_headers.status_code == 200    # ❌ fixture 状态应在 fixture fail-fast，不应在 helper
    result = await create_category(...)
    assert result.status_code == 201                # ❌ 若测「重复类目名 422」，此 helper 不可用
    assert result.body is not None
    return result.body.id                           # ❌ 只返 id，丢失 CategoryResult

async def _create_product(...) -> ProductResponse:
    ...
    assert response.status_code == 201              # ❌ 负向测 POST /products 无法用这个 helper
    return ProductResponse.model_validate(...)
```

对比 **较规范** 的 `register_user`（`conftest.py`）——如实返回，不 assert：

```python
async def register_user(client, ...) -> RegisterResult:
    response = await client.post("/auth/register", ...)
    return RegisterResult(
        status_code=response.status_code,           # ✅ 422 也能返回
        body=_parse_token_body(response),
        ...
    )
```

Case 里 `test_register_duplicate_email_returns_422` 才能对 **同一 helper** 断言 422。

### 应怎么做

- 原子 helper：**只返** `*Result`（含 `status_code`）。
- Setup 成功前提：由 **fixture fail-fast** 保证，不在 helper 里 assert 201。

## 反模式 3：组合 helper 返回 Context（数据流倒置）

### 错在哪

规范分工应是：**helper → Result / PipelineResult**；**fixture → Context**。  
`register_and_open_shop` 作为 **orchestrator** 却直接构造并返回 `ShopOwnerContext`，把 **fixture 该干的装配** 塞进 support，且与 **单步 `RegisterResult`/`ShopResult`** 模型重复。

### 案例：`register_and_open_shop`

```python
async def register_and_open_shop(...) -> ShopOwnerContext:   # ❌ helper 返 Context
    registered = await register_user(client, ...)
    auth = _auth_context_from_register(registered)              # ❌ 在 helper 路径上 Result→胖 Context
    ...
    if registered.status_code != 201:
        return ShopOwnerContext(                              # ❌ 失败 Context 可能被 fixture 透传
            status_code=failed_status,
            auth=auth,
            headers={},                                       # ❌ 空 headers 仍注入 Case
            ...
        )
    shop_result = await create_shop(client, headers=auth.headers, ...)
    return ShopOwnerContext(                                  # ❌ 再次摊平成胖对象
        status_code=shop_result.status_code,
        auth=auth,
        shop=shop_result.body,
        headers=auth.headers,                                 # ❌ 存储型 headers 拷贝
        ...
    )

@pytest.fixture
async def shop_owner(client) -> ShopOwnerContext:
    return await register_and_open_shop(client)               # ❌ 无 fail-fast，失败也注入
```

### 应怎么做

```text
register_and_open_shop(...) -> PipelineResult(steps=(RegisterResult, ShopResult))

shop_owner fixture:
    root = await register_and_open_shop(client)
    if root.step(ShopResult).status_code != 201:
        pytest.fail(...)
    return ShopOwnerContext(root=root)
```

## 反模式 4：Context 嵌套 + 存储型字段（与 Result 双份、易 stale）

### 错在哪

- `RegisterResult` 已有 `body.access_token`，`AuthContext` 再存 `access_token`、`headers` → **同一份信息两份拷贝**。
- `ShopOwnerContext` 再嵌套 `auth: AuthContext`，又复制 `shop`、`headers`、`email` → **composite 字段名膨胀**（反模式 3 的延续）。
- 若日后从 `body` 更新 token，`headers` dict **不会自动同步**。

### 案例：`_auth_context_from_register` + `ShopOwnerContext`

```python
def _auth_context_from_register(registered: RegisterResult) -> AuthContext:
    access_token = registered.body.access_token
    return AuthContext(
        ...
        access_token=access_token,
        headers=auth_headers(access_token),     # ❌ 存储拷贝；应 read-only 投影
        user=registered.body.user,
    )

@dataclass
class ShopOwnerContext:
    auth: AuthContext                           # ❌ Context 嵌套 Context
    shop: ShopResponse | None                   # ❌ 与 body 重复
    headers: dict[str, str]                     # ❌ 又与 auth.headers 重复
    status_code: int                            # 开店步 status，但 auth 里还有注册步 status
```

Case 访问路径混乱，例如：

```python
shop_owner.headers          # 从 Context 拷贝取
shop_owner.shop.id          # 从 Context 字段取
shop_owner.auth.status_code # 注册步要从嵌套取
shop_owner.status_code      # 开店步 status —— 两步 status 命名易混
```

### 应怎么做

- `ShopOwnerContext` 仅 `root: PipelineResult`。
- 取 token：`bearer_headers(shop_owner.root.step(RegisterResult))`。
- 取 shop：`shop_owner.root.step(ShopResult).body`。

## 反模式 5：Setup fixture 不 fail-fast（失败世界进入 Case）

### 错在哪

**Setup fixture** 应只注入 **happy-path 前置世界**。失败场景应在 Case 里调 helper 并 assert，而不是让 fixture 塞入「半失败 Context」。

### 案例：`shop_owner` vs `admin_auth_headers`（同文件两种风格）

**✅ 相对正确** — `admin_auth_headers` 会 fail-fast：

```python
@pytest.fixture
async def admin_auth_headers(client) -> AdminAuthContext:
    logged_in = await login_user(client, email=..., password=...)
    if logged_in.status_code != 200 or logged_in.body is None:
        pytest.fail("seed 管理员登录失败...")   # ✅ 失败不进入 Case
    ...
```

**❌ 问题** — `shop_owner` 直接透传，且 orchestrator 可能返回失败 Context：

```python
@pytest.fixture
async def shop_owner(client) -> ShopOwnerContext:
    return await register_and_open_shop(client)  # ❌ 注册失败时 headers={} 仍注入 Case

# Case 里被迫写防御性断言，而非假定 Setup 已成功：
async def test_create_product_success(..., shop_owner):
    assert shop_owner.status_code == 201           # ❌ 本应由 fixture 保证
    assert shop_owner.shop is not None
```

### 应怎么做

- `shop_owner` / `authenticated_user` 与 `admin_auth_headers` 一致：**Setup 失败 → pytest.fail**。
- 测「开店失败 422」等：**不用** `shop_owner` fixture，Case 内 `await create_shop(...)` 再 assert。

## 反模式 6：DB seed 写在 test 文件

### 错在哪

直写 SQL / 建 engine 属于 **Support（seeds）** 职责，放在 Case 文件会导致：

- 其他 Case 无法复用（或再次复制粘贴）；
- test 文件承担 I/O 细节，违背 Case 层「主要是 assert」。

### 案例：`_seed_inactive_user`

`tests/user/test_login.py`：

```python
async def _seed_inactive_user(database_url: str, email: str, password: str) -> None:
    engine = create_async_engine(database_url)    # ❌ test 内建连库逻辑
    async with engine.begin() as conn:
        await conn.execute(text("INSERT INTO users ..."), {...})  # ❌ 原始 SQL seed
    await engine.dispose()

async def test_login_inactive_user_returns_403(client, database_url: str):
    await _seed_inactive_user(database_url, email=..., password=...)  # ❌ 仅本文件可用
    result = await login_user(client, ...)
    assert result.status_code == 403                # ✅ Case 断言本身是对的
```

### 应怎么做

- 迁至 `tests/testkit/db/user.py`：`seed_inactive_user(...)`。
- Case 只保留 Arrange 调用 + Act + Assert。
